### 🧠 Concept

Django is a **web framework** written in Python. A web framework is basically a toolkit that handles the repetitive, boring, error-prone parts of building a website — so you focus on your app's actual logic instead of reinventing things like:

- How to parse an incoming HTTP request
- How to talk to a database safely
- How to render HTML dynamically
- How to protect against common security holes (SQL injection, CSRF, XSS)

**Why does Django need to exist?** Without it, every time you build a website you'd have to hand-write code to listen for HTTP requests, parse URLs, connect to a database, generate HTML, handle forms, manage user logins, etc. Django gives you battle-tested tools for all of that.

**Real-world usage:** Instagram, Pinterest, Mozilla, and thousands of SaaS backends run on Django. It's especially popular for content-heavy sites and APIs.

### 📚 Necessary Theory — MVT Pattern

Django follows a pattern called **MVT (Model-View-Template)** — Django's flavor of the more famous MVC pattern.

| Piece | Role |
|---|---|
| **Model** | Defines your data structure (maps to database tables) |
| **View** | Contains your logic — decides *what data* to fetch and *what response* to send |
| **Template** | The HTML — decides *how* data is displayed |

The flow looks like this:

```
Browser sends request
      ↓
   URLconf (urls.py) — "which view handles this URL?"
      ↓
     View (views.py) — "what data do I need? what logic runs?"
      ↓
   Model (models.py) — talks to Database, fetches/saves data
      ↓
     View — decides response
      ↓
   Template (.html) — renders data into HTML
      ↓
Browser receives HTML response
```

This is the single most important mental model in Django. Everything else builds on it.

### 🔍 Under the Hood

When you type a URL and hit enter, here's roughly what happens inside Django:
1. Django's WSGI/ASGI server receives the raw HTTP request.
2. Django checks `urls.py` to match the URL path to a specific **view function**.
3. That view function runs your Python code — maybe queries the database via a **model**.
4. The view returns an `HttpResponse` — often generated by rendering a **template** with data.
5. That response (usually HTML) is sent back to the browser.

Q2 urls.py is the map — URL path in, matching view out.

Q3 — 
Separation of concerns. If you mixed data logic and display logic together, you'd get problems like:

Same product data needs to render differently in 3 places — an HTML page, a JSON API response, an admin dashboard. If display logic is baked into the Model, you'd have to duplicate/hack around it for each case.
A designer changing button colors in the Template shouldn't ever risk touching how data is fetched from the database, and vice versa — a DB schema change shouldn't force you to rewrite HTML.
It makes each piece independently testable — you can test "does this query return the right data" without rendering any HTML at all.

So the real reason isn't just "they contain different things" — it's that keeping them separate means you can change one without breaking the other. This is a core professional principle.
